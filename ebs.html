EBS: disks you can attach, grow and back up

Add a second disk to a running server, format and mount it so it survives reboots, grow it without downtime, and restore a deleted file from a snapshot, including the duplicate-UUID trap.

By @usmanrangrez · Nov 2026 · Account IDs, IPs and keys in examples are placeholders

Follows M Prashant's AWS in One Video at 2:00:12. The text and labs are my own write-up, not a transcript.

01

What EBS is

EBS volumes are network disks attached to EC2, like an external SSD: you can detach and reattach them, grow them, and copy them (snapshots). That's why files survived stop/start in the EC2 chapter.

Field (root disk) Value Meaning
Type gp3 General purpose SSD (default)
IOPS / throughput 3000 / 125 MB/s gp3's free baseline
Availability Zone eu-central-1b A disk only attaches to servers in the same AZ
Snapshot ID snap-… The root disk was copied from the AMI's snapshot
Delete on termination Yes Terminating the server deletes this disk

Other types: io2 (high-IOPS databases), st1 (throughput HDD), sc1 (cold HDD). AZ names (eu-central-1b) differ per account; AZ IDs (euc1-az3) are the real location.

Device names: AWS labels like /dev/xvda (Xen virtual disk) or /dev/sdf are just slots. On Nitro instances Linux sees NVMe names: nvme0n1, nvme1n1… Always check from inside with lsblk.

02

Lab: add, format and mount a second disk

LAB · CONSOLE + SERVER
  1. Console: Volumes → Create volume: gp3, 2 GiB, same AZ as the server → Attach to the instance (/dev/sdf).
  2. lsblk → a 2G disk with no mountpoint. sudo file -s /dev/nvme1n1 → data means empty, safe to format.
  3. sudo mkfs -t xfs /dev/nvme1n1 (double-check it's not nvme0n1!) → file -s now says XFS.
  4. sudo mkdir /data && sudo mount /dev/nvme1n1 /data → df -h /data shows 2.0G (47M is filesystem bookkeeping).
  5. echo "hello from my data disk" | sudo tee /data/hello.txt → lsblk shows /data.
03

The reboot trap and /etc/fstab

After sudo reboot, /data was empty and unmounted: a manual mount only lasts until reboot. The file was safe on the disk, just not connected. Disk order also shuffled between reboots, so mount by UUID, not by name.

bash
sudo blkid /dev/nvme1n1                       # UUID="05301bb5-…" TYPE="xfs"
sudo cp /etc/fstab /etc/fstab.bak             # back up first: a broken fstab can stop boot
echo 'UUID=05301bb5-…  /data  xfs  defaults,nofail  0  2' | sudo tee -a /etc/fstab
sudo mount -a                                 # test the line before rebooting
Field Meaning
UUID=… The disk's permanent ID
/data · xfs Mount point · filesystem
defaults,nofail nofail = boot anyway if the disk is missing (important on AWS)
0 2 Old dump flag · check order at boot

After another reboot /data and the file came back automatically.

UI or terminal? Creating, attaching, resizing and snapshotting are AWS jobs (console or CLI). Formatting, mounting and fstab happen inside Linux, so only on the server (SSH, Instance Connect or Session Manager). In companies this is scripted in user data or Ansible; on Kubernetes it's automatic.

04

Grow a disk without downtime

  1. Console: Volume → Modify → 2 → 3 GiB (only bigger, and then wait ~6 h before modifying again). Usable once "optimizing".
  2. lsblk showed 3G but df -h /data still 2.0G: the filesystem doesn't know yet.
  3. sudo xfs_growfs -d /data → data blocks changed from 524288 to 786432 (×4 KB = 2 → 3 GiB). Files untouched.

For ext4: sudo resize2fs /dev/nvme1n1. For the root disk (has a partition): sudo growpart /dev/nvme0n1 1 then sudo xfs_growfs -d /. On-call "disk full" fixes look exactly like this; good teams add alerts at 80% and keep data off servers.

05

Snapshots: backup and restore

Snapshots are point-in-time copies stored by AWS in S3, incremental, region-wide (no AZ), copyable to other regions. Mine was 70.5 MiB for a 3 GiB disk: you pay for stored data only.

LAB · RESTORE A DELETED FILE
  1. Volume → Create snapshot → data disk with hello.txt → Completed.
  2. Disaster: sudo rm /data/hello.txt (no recycle bin in Linux).
  3. Snapshot → Create volume from snapshot (gp3, 3 GiB, eu-central-1b) → attach (/dev/sdg → nvme2n1).
  4. sudo mount /dev/nvme2n1 /restore → wrong fs type, bad option, bad superblock… (misleading).
  5. sudo dmesg | tail -3 → Filesystem has duplicate UUID … can't mount: the snapshot copied the UUID too.
  6. sudo mount -o nouuid /dev/nvme2n1 /restore → hello.txt is there → sudo cp /restore/hello.txt /data/ → sudo umount /restore.

Restoring never overwrites the original: it always creates a new disk. Lose one file → mount the copy and copy back; lose the whole disk → swap disks.

07

Interview questions

You attached an EBS volume and after a reboot the data is gone. Why?

It was mounted manually and not added to /etc/fstab, so it wasn't remounted. The data is still on the volume. Add an fstab entry by UUID with nofail and test with mount -a.

Can you attach an EBS volume to an instance in another AZ?

No. Snapshot it and create a new volume from the snapshot in the target AZ.

How do you increase disk space on a running instance?

Modify the volume size, then grow the partition (growpart, for disks with partitions) and the filesystem (xfs_growfs or resize2fs). No downtime.

Restored volume won't mount: "wrong fs type". Likely cause?

Duplicate XFS UUID when the original is mounted on the same server. dmesg confirms it; mount with -o nouuid or regenerate the UUID with xfs_admin -U generate.

How are EBS snapshots billed?

Incrementally: only changed blocks are stored after the first snapshot, billed per GB-month.
