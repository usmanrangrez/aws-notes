AWS IAM From Zero: 6 Hands-On Labs

I learned AWS IAM in one long session by building things in a real account, from locking down a brand-new account to deploying from GitHub with no stored keys. This is that session written up as a guide: the concepts, every lab with real outputs, the mistakes I made (including leaking a key) and how each one is handled in production.

Complete beginners to AWS, and anyone heading into a DevOps or cloud role who wants to really understand IAM rather than just click through it. You don't need any prior AWS experience. Basic comfort with a terminal helps for Labs 3 and 5.

Cost

Everything here is free except Lab 3, which runs a t3.micro server for a few minutes (cents, or covered by credits). Accounts created since July 2025 choose between a Free plan and a Paid plan. On the Free plan you can't be charged: the account closes after 6 months or when the credits run out, whichever comes first, and AWS keeps your data for 90 days in case you upgrade. Five safety rules for every lab

1. Turn on MFA for root first and stop using root (Lab 1).

2. On a Paid plan, create a budget alert before anything else (Billing → Budgets → Use a template → Zero spend budget).

3. Use one region for everything, so you can't forget resources somewhere else.

4. Never paste access keys or secrets anywhere: not in chats, tickets, screenshots or code. I did this by accident while testing; section 11 covers what happened.

5. If you stop partway, run the cleanup checklist. At minimum, terminate any EC2 instance and delete any access keys.

How to get the most out of the labs

The test tables list a result for each step. Cover the result column and predict ✓ or ✗ before you try it, then work out why. Making that guess, and sometimes getting it wrong, is where IAM actually clicks. My own wrong guesses are marked in the tables.

01

What IAM is

IAM is the security desk of an AWS account. Every request to AWS, whether a console click, a CLI command or an app's SDK call, passes two checks:

1 · Authentication

Who are you? Password + MFA, an access key, or temporary credentials from a role.

2 · Authorization

Are you allowed to do this? IAM evaluates every policy that applies and answers allow or deny.

Global & free

IAM isn't tied to a region and costs nothing. One set of users and roles covers the whole account.

The one sentence to remember

Who (principal) can do what (action) on which thing (resource) under which conditions.

The office-building analogy

AWS thingBuilding analogy
AWS accountThe office building
Root userThe owner, with a master key to every door, the safe and the bank account. Can't be restricted.
IAMThe security desk deciding who gets in and which doors open
IAM userAn employee with their own ID card
IAM groupA team. Permissions given to the team apply to everyone in it.
PolicyA permission slip ("may open these doors")
IAM roleA hat / visitor badge someone borrows for a while; it has its own powers
02

The building blocks

ThingWhat it isUsed in production?
Root userThe sign-up email. Can do everything; IAM policies can't restrict it.Lock it away with MFA. Never use it day to day.
IAM userA long-lived identity with a password and/or access keys (AKIA…).Less and less. Humans use IAM Identity Center (SSO) instead.
IAM groupA collection of users that share policies. Not an identity: you can't log in as a group.Yes, wherever IAM users exist.
IAM roleAn identity with no permanent credentials. Someone or something assumes it and gets temporary keys (ASIA…).The most important thing in production. Used by EC2, Lambda, CI/CD, SSO and cross-account access.

STSSecurity Token Service: hands out temporary credentials when a role is assumed.Behind every role.
Rule of thumb

Humans log in through SSO, then use roles. Machines use roles. Avoid long-lived access keys.

Lab: Secure a brand-new account

This is the first thing every company does with a new AWS account. Do it before anything else in this guide.

LAB 1 · CONSOLE

A. Put MFA on the root user

  1. Install Google or Microsoft Authenticator on your phone.
  2. Account name (top right) → Security credentials → Assign MFA device → name root-phone → Authenticator app.
  3. Scan the QR code, then enter two consecutive codes → Add MFA.

B. Create your own admin user (via a group)

  1. IAM → Users → Create user → name my-admin → tick Provide console access → I want to create an IAM user → custom password.
  2. Add user to group → Create group Admins → tick AdministratorAccess. Several policies match the search; pick the plain one, type AWS managed – job function.
  3. Leave permissions boundary off → Create user.
  4. Save the sign-in URL: https://123456789012.signin.aws.amazon.com/console

C. Let IAM users see billing

  1. As root: account name → Account → IAM user and role access to Billing information → Edit → Activate IAM Access.

D. Switch to the admin user

  1. Sign out of root, log in at the sign-in URL as my-admin.
  2. IAM → Users → my-admin → Security credentials → add MFA (my-admin-phone).
  3. Pick one region and stick with it (Frankfurt, eu-central-1). Use EC2 Global View to spot forgotten resources in any region.

04

Policies: reading the JSON

A policy is a short JSON document. The AWS managed policy AdministratorAccess is the simplest one there is:

json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Action": "*",
      "Resource": "*"
    }
  ]
}

It reads: allow every action on every resource. Compare it with AmazonS3ReadOnlyAccess:

json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Action": ["s3:Get*", "s3:List*", "s3:Describe*"],
      "Resource": "*"
    }
  ]
}

Every field

FieldMeaning
VersionAlways 2012-10-17. It's the policy-language version, not a date you change.
StatementThe list of rules
SidOptional label for humans, e.g. "UploadOnlyToLabBucket". Changes nothing.
EffectAllow or Deny
ActionAPI calls, written service:Action. Wildcards work: s3:Get* = every action starting with Get.
ResourceARNs of the things the rule applies to. * = everything.
ConditionOptional "…but only if…" rules: MFA, IP, region, tags, repo/branch…
PrincipalOnly in resource-based policies (bucket policies, role trust policies): who is allowed

Why does a managed policy use "Resource": "*"?

  • AWS writes managed policies once for millions of customers, so it can't know your bucket names.
  • * only covers what you can reach anyway: your own account's buckets. Other people's buckets stay blocked unless their bucket policy lets you in.
  • Some actions only work with *, e.g. s3:ListAllMyBuckets isn't about one bucket.
  • In production you write your own policy naming the exact bucket. That's least privilege.

ARN anatomy

An ARN (Amazon Resource Name) is the unique address of anything in AWS.

arnalways: awspartition: s3service:  region (empty):  account (empty): iam-lab-123456789012bucket /*every file inside
arn:aws:iamservice: region (IAM is global):123456789012account:role/lab-ec2-s3-readertype/name
The #1 S3 policy mistake

Listing files is an action on the bucket: arn:aws:s3:::my-bucket (no /*).

Reading or uploading files is an action on the files: arn:aws:s3:::my-bucket/*.

my-bucket:* (colon instead of slash) matches nothing.

Labels you'll see in the console: AWS managed – job function (made for a typical job role), Used as: None / Permissions policy (whether it's attached anywhere), IAMUserChangePassword (added automatically when "must create new password" is ticked).

Lab: Least privilege, implicit deny & explicit Deny

Goal: a test user test-viewer who can only look at S3, then exactly one extra permission, then a Deny that beats full access.

LAB 2 · CONSOLE

Setup

  1. As my-admin: S3 → create bucket iam-lab-123456789012 (Frankfurt, defaults, "Block all public access" ON) and upload a small file. Bucket names are global, so add your account ID to make them unique.

07

Roles explained

A user is who you are (a permanent ID card). A role is a hat you put on for a while, with its own powers.

Rule 1

While wearing the hat you have only the hat's permissions. Yours, including your Denys, are set aside.

Rule 2

Take it off ("Switch back", or the session expires) and you're back to your own permissions.

Rule 3

Not everyone may wear it: the role's trust policy must allow you (and for accounts, your own policy too).

Rule 4

You get temporary keys from STS (ASIA…) that expire: 1 h by default for people, a few hours for EC2, auto-renewed for services.

Every role has two policies

Who can be trusted

Trusted entityPrincipalThe "other side"Real use
AWS service"Service": "ec2.amazonaws.com"Whoever attaches the role needs iam:PassRoleEC2, Lambda (lambda.amazonaws.com), ECS (ecs-tasks…)

Specific user/role"AWS": "arn:aws:iam::ACCOUNT:role/ci-deployer"Only that exact identityOne fixed machine identity
Web identity (OIDC)"Federated": "…oidc-provider/…"The outside system's signed token + conditionsGitHub Actions, EKS pods
SAML / SSOCompany identity providerOkta / Entra / Google loginEmployees via Identity Center

arn:aws:iam::123456789012:root in a trust policy means "this whole account; its own IAM policies decide which users may assume me".

Lab: An EC2 server reads S3 with no keys

The problem: an app on a server needs S3. Pasting access keys into code risks leaks (GitHub, screenshots, ex-employees), the keys never expire, and nobody rotates them. The solution: attach a role to the server.

LAB 3 · CONSOLE + SHELL

A. A read-only policy for one bucket

json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "ListFilesInLabBucket",
      "Effect": "Allow",
      "Action": "s3:ListBucket",
      "Resource": "arn:aws:s3:::iam-lab-123456789012"
    },
    {
      "Sid": "ReadFilesInLabBucket",
      "Effect": "Allow",
      "Action": "s3:GetObject",
      "Resource": "arn:aws:s3:::iam-lab-123456789012/*"
    }
  ]
}

Name: lab-read-iam-lab-bucket. It has two statements because listing acts on the bucket and reading acts on the files.

B. The role

  1. IAM → Roles → Create role → AWS service → EC2. This writes the trust policy for you.
  2. Attach lab-read-iam-lab-bucket → name lab-ec2-s3-reader.
  3. The Trust relationships tab shows "Principal": {"Service": "ec2.amazonaws.com"}, "Action": "sts:AssumeRole".

C. Launch a server with the role

  1. EC2 → Launch instance → lab-role-test · Amazon Linux 2023 · t3.micro · Proceed without a key pair · default network. "Allow SSH from anywhere" is acceptable only because this server lives for a few minutes; never leave it like that on a real server.
  2. Advanced details → IAM instance profile → lab-ec2-s3-reader. This is the step that attaches the role.
  3. Connect → EC2 Instance Connect (a browser terminal).

E. See the temporary keys (IMDSv2)

bash
TOKEN=$(curl -s -X PUT "http://169.254.169.254/latest/api/token" \
  -H "X-aws-ec2-metadata-token-ttl-seconds: 300")
curl -s -H "X-aws-ec2-metadata-token: $TOKEN" \
  http://169.254.169.254/latest/meta-data/iam/security-credentials/lab-ec2-s3-reader \
  | grep -E '"(Type|AccessKeyId|LastUpdated|Expiration)"'

  "LastUpdated" : "2026-11-15T15:43:37Z",
  "Type"        : "AWS-HMAC",
  "AccessKeyId" : "ASIA…",
  "Expiration"  : "2026-11-15T22:17:54Z"      # ~6.5 h later, renewed automatically
Never paste a SecretAccessKey or Token anywhere

The grep above deliberately hides them. Treat them like passwords.

Why IMDSv2 (the token step) exists

In 2019 Capital One was breached when an attacker tricked a web app (SSRF) into fetching these keys from 169.254.169.254. IMDSv2's PUT-token step blocks that trick. Companies enforce IMDSv2 on every server, and Amazon Linux 2023 uses it by default.

F. Change permissions live

Attach lab-upload-iam-lab-bucket to the role, wait about 10 s, and re-run the upload → ✓ allowed, with no restart and no change on the server. Edit the role once, and every server using it is updated.

G. Clean up

EC2 → instance → Terminate. Terminated instances stay listed for about an hour, then disappear, and cost nothing. Stopped is different: the server and its disk still exist.

Questions I asked

Do I need to remember the temporary key?

No, never. The CLI and every SDK (boto3, Node, Java…) fetch it from IMDS automatically and pick up new keys before expiry. Your code just calls boto3.client("s3"). To see the full key (for learning only), run the curl without | grep.

When is that key useful?

For you: almost never, apart from debugging which role a server uses. For an attacker: very useful, since the three values (AccessKeyId + Secret + Token) work from anywhere until they expire. That's why IMDSv2, least privilege, and alerts on role keys used from outside AWS exist.

How does EC2 keep the role for days?

It doesn't hold one long session. The EC2 service assumes the role, gets keys valid for about 6 h, places them in IMDS, and repeats before they expire, for as long as the role stays attached. The role's "Maximum session duration" (1–12 h) is for people and scripts calling AssumeRole.

Instance profile vs role?

EC2 can't hold a role directly. An instance profile is a small wrapper containing the role. The console creates one with the same name automatically when you make an "EC2" role; in Terraform or CloudFormation you create it yourself (aws_iam_instance_profile).

iam:PassRole: who is allowed to attach a role

Without this check, a limited developer could launch a server with an admin role, log into it and use the admin keys. Companies restrict it like this:

json
{
  "Effect": "Allow",
  "Action": "iam:PassRole",
  "Resource": "arn:aws:iam::123456789012:role/lab-ec2-s3-reader",
  "Condition": {
    "StringEquals": { "iam:PassedToService": "ec2.amazonaws.com" }
  }
}

Reads: "you may attach only this role, and only to EC2."

Lab: A person switching into a role

In companies, an engineer's normal login is read-only. When they actually need to change something, they switch into a more powerful role, do the job, and switch back. Every switch is logged.

LAB 4 · CONSOLE
  1. Reset test-viewer: remove AmazonS3FullAccess and lab-upload-iam-lab-bucket. Keep ReadOnly + deny-delete-lab-files.

Why not just give the user the permissions directly?

ReasonDirect permissionsRole switching
AccidentsOne wrong click deletes production dataRead-only by default; you have to decide to switch

How it's used in companies

On-call: the role prod-admin trusts the account, and the group OnCall gets sts:AssumeRole on it. People join or leave the group; the role never changes.

Cross-account: the prod account (111) has a role that trusts the login account (222); account 222 decides which of its people may use it.

Tools like Identity Center and approval workflows ("request prod access for 2 h") all use role switching underneath.

Lab: GitHub Actions → AWS with no keys (OIDC)

The same "hat" idea again, except this time the wearer is a GitHub workflow run, and it proves who it is with a signed ID card (an OIDC token).

LAB 5 · AWS + GITHUB
  1. GitHub: new private repo aws-oidc-lab with a README.
  2. Trust GitHub's ID cards: IAM → Identity providers → Add → OpenID Connect · URL https://token.actions.githubusercontent.com · audience sts.amazonaws.com.
  3. Bucket oidc-lab-123456789012 and policy oidc-lab-s3-deploy (ListBucket on the bucket + PutObject on /*).
  4. Role: IAM → Roles → Create → Web identity → provider above · audience · GitHub org = YOUR_GH_USER · repo · branch main → attach the policy → name github-actions-oidc-lab.
  5. Workflow: add .github/workflows/deploy.yml (below) → commit to main → Actions tab.
yaml

on:
  push:
    branches: [main]
  workflow_dispatch:        # adds a "Run workflow" button

  id-token: write           # REQUIRED: lets the run request the OIDC ID card

        run: |
          TOKEN=$(curl -s -H "Authorization: bearer $ACTIONS_ID_TOKEN_REQUEST_TOKEN" "$ACTIONS_ID_TOKEN_REQUEST_URL&audience=sts.amazonaws.com" | jq -r .value)
          python3 -c "import sys,json,base64;p=sys.argv[1].split('.')[1];p+='='*(-len(p)%4);c=json.loads(base64.urlsafe_b64decode(p));print(json.dumps({k:c.get(k) for k in ('sub','aud','repository','ref')},indent=2))" "$TOKEN"

      - name: Get AWS credentials via OIDC

        with:
          role-to-assume: arn:aws:iam::123456789012:role/github-actions-oidc-lab

The debugging method that always works

Print what the caller actually sends (the token's sub), put it next to what the trust policy expects, and compare character by character. Wizards and tutorials can be out of date: the AWS wizard still wrote the old sub format. Searching the exact error led to the explanation (configure-aws-credentials #1137).

Why GitHub added the IDs, and which repos are affected

If you deleted or renamed a repo, someone else could create one with the same name and match your trust policy. IDs can never be reused, so only that exact repo matches.

Per GitHub's changelog, repositories created (or renamed or transferred) after July 15, 2026 use the new format automatically. Older repos keep the classic repo:owner/repo:… format unless you opt in under Settings → Actions → OIDC. Check what a repo sends with:

bash
gh api /repos/OWNER/REPO/actions/oidc/customization/sub
Other causes of the same error

Wrong case in the username (StringEquals/StringLike are case-sensitive) · branch is master not main · jobs using environment: get …:environment:<name> instead of :ref: · typo in role-to-assume · wrong provider URL or audience.

A wildcard like repo:YOUR_GH_USER/aws-oidc-lab:* (with StringLike) is acceptable. Never use repo:*.

Branch protection test

Created branch test → Actions → Run workflow from test → ✗ Not authorized. The card said …ref:refs/heads/test, and the role only accepts main. Only reviewed code on main can deploy.

Action versions shown (checkout@v5, configure-aws-credentials@v6) were current in Nov 2026; check each action's releases page for newer ones. Access keys (old way) vs OIDC, and a real key leak

The old way, in 4 steps

  1. IAM user ci-deployer with no console access and the same least-privilege policy.
  2. Security credentials → Create access key → use case "Application running outside AWS". AWS itself shows alternatives here; the secret is shown only once.
  3. GitHub → Settings → Secrets → AWS_ACCESS_KEY_ID, AWS_SECRET_ACCESS_KEY.
  4. Workflow:
yaml
      - uses: aws-actions/configure-aws-credentials@v6
        with:
          aws-access-key-id: ${{ secrets.AWS_ACCESS_KEY_ID }}
          aws-secret-access-key: ${{ secrets.AWS_SECRET_ACCESS_KEY }}
          aws-region: eu-central-1
What actually happened: I leaked a real key

While testing, I pasted the real secret access key into an AI chat twice, once while copying CloudShell output and again while fixing a typo. Anything pasted into a chat, ticket, Slack or log counts as leaked.

Correct response (done): IAM → user → Security credentials → key → Deactivate → Delete → verify it fails (InvalidClientTokenId) → rm -rf ~/.aws in CloudShell → check CloudTrail for what the key did → create a new key only if still needed.

With OIDC this can't happen: there's no permanent secret to paste.

In one sentence

With keys you guard a secret forever; with OIDC there is no secret, just a trust rule saying "this repo, this branch".

Why companies still have keys, and how to handle them

Old pipelines, tools without OIDC support, machines outside AWS (e.g. on-prem Jenkins). GitHub Actions, GitLab, Bitbucket, CircleCI and Azure DevOps all support OIDC, so new setups should use it.

  • One IAM user per pipeline, never a shared or personal user
  • Least privilege on that user
  • Keys only in a secret store (GitHub Secrets, Secrets Manager, Vault), never in code
  • Rotate (e.g. every 90 days) and check "Access key last used"; delete unused keys
  • Leak → deactivate immediately → CloudTrail → replace
  • Plan the migration to OIDC

CloudTrail & auditing: who did what

CloudTrail records every API call (console clicks included): who, what, when, from which IP, and whether it worked.

Event history

On by default, free, last 90 days of management events. No trail needed.

Not included by default

S3 file reads and uploads (data events) need a trail with data events, which costs money.

Region tip

IAM and sign-in events are often in N. Virginia (us-east-1). If a search is empty, switch region.

LAB 6 · CONSOLE
  1. CloudTrail → ☰ → Event history. Don't click "Create a trail"; you don't need one for this.
  2. Filter Event name = AssumeRoleWithWebIdentity → see every GitHub run; failed ones carry an error code.
  3. Open one → Event record (JSON) → read userIdentity.type (WebIdentityUser), identityProvider, requestParameters.roleArn, errorCode/errorMessage, sourceIPAddress.
  4. Filter AWS access key = the leaked AKIA… → see everything it did, and from which IPs. An unknown IP would mean an attacker.
  5. Filter Event name = CreateAccessKey / DeleteAccessKey → who created or removed keys, and when.
  6. IAM → Credential report → Download CSV → check mfa_active, access_key_1_last_used_date, password_last_used.
How companies run it

An organization-wide trail sends every account's logs to a locked S3 bucket in a separate log-archive account, kept for years.

Alerts fire on: root login, CreateAccessKey, break-glass role use, StopLogging.

Big searches use Athena (SQL over the logs in S3) or CloudWatch. CloudTrail Lake closed to new customers on May 31, 2026.

Also useful: IAM Access Analyzer (finds unused permissions and resources shared outside the account) and the Last accessed tab on users and roles (which services were actually used).

Conditions, boundaries, Identity Center, SCPs

1 · Conditions: "…but only if…"

json
{
  "Effect": "Allow",
  "Action": "ec2:TerminateInstances",
  "Resource": "*",
  "Condition": {
    "Bool":         { "aws:MultiFactorAuthPresent": "true" },
    "StringEquals": { "aws:ResourceTag/env": "dev" }
  }
}

Reads: "may delete servers, but only with MFA and only servers tagged env=dev." Keys inside one condition block are AND; several values for one key are OR.

Condition keyTypical use
aws:MultiFactorAuthPresentDangerous actions require MFA
aws:SourceIp / aws:SourceVpcOnly from the office, VPN or our network
aws:RequestedRegionOnly allowed regions (e.g. EU for GDPR)
aws:ResourceTag/… + aws:PrincipalTag/…ABAC: team A only touches resources tagged team=A
aws:PrincipalOrgIDOnly identities from our own organization
iam:PassedToServicePassRole only to a specific service
token.actions.githubusercontent.com:subOIDC: only this repo and branch

2 · Permission boundaries: a ceiling

Developers need to create roles for their Lambda functions, but must not be able to create an admin role. Rule: "you may create roles only if you attach the boundary dev-boundary."

Effective permissions = role's policy ∩ boundary. Even if AdministratorAccess is attached, the role can only do what the boundary allows. A boundary never grants anything.

3 · IAM Identity Center: how people really log in

Employee → company login (Okta / Entra / Google) → AWS access portal → picks "Prod – ReadOnly" or "Dev – PowerUser" → gets a temporary role session.

  • Permission sets are templates that become a role in each account.
  • Offboarding happens in one place, and access is gone everywhere.
  • No IAM users or passwords in AWS. On the CLI: aws configure sso, which gives temporary keys.
  • As a DevOps engineer you'll use it daily as a user; the platform team usually sets it up.

4 · AWS Organizations & SCPs: guardrails for whole accounts

Organizations groups many accounts (prod, dev, logs, security) into OUs. SCPs set the maximum for everyone in an account, even its admins.

json
{
  "Effect": "Deny",
  "Action": "*",
  "Resource": "*",
  "Condition": {
    "StringNotEquals": { "aws:RequestedRegion": ["eu-central-1", "eu-west-1"] }
  }
}

Free plan note: joining or creating an organization automatically upgrades a Free plan account to Paid, so this part is theory-only in the labs.

Other typical SCPs: deny stopping CloudTrail, deny leaving the organization, deny creating IAM users. If you see …with an explicit deny in a service control policy, adding permissions won't help; ask the platform team. SCPs don't apply to the management account.

Interview Q&A

User vs role?

A user is a permanent identity with long-term credentials (password / AKIA keys). A role has no credentials of its own; it's assumed temporarily and STS issues short-lived ASIA keys.

Trust policy vs permissions policy?

The trust policy (resource-based, with a Principal) says who can assume the role. The permissions policy says what the role can do. Both must allow it.

How does AWS evaluate a request?

Default implicit deny → if any explicit Deny matches, it's denied → otherwise, if an Allow matches (and SCPs, boundaries and session policies permit it), it's allowed → otherwise denied.

Implicit vs explicit deny, and how do you tell them apart?

Implicit: nothing allowed it ("no identity-based policy allows"), so you add the permission. Explicit: a Deny statement matched ("with an explicit deny in …"), so you have to change the Deny or SCP itself.

How does an app on EC2 get AWS credentials?

Through an IAM role attached via an instance profile. The EC2 service assumes the role and serves temporary, auto-rotating keys through the metadata service (169.254.169.254) with IMDSv2 enforced. The SDK picks them up automatically, so nothing is stored.

What is iam:PassRole and why does it exist?

The permission to attach a role to a service (EC2, Lambda, ECS…). It's checked on the person doing the attaching, and it prevents privilege escalation (a limited user attaching an admin role to their own server or function). Restrict it to specific role ARNs and iam:PassedToService.

How do you give access to another account?

Create a role in the target account whose trust policy trusts the source account (or a specific role in it). The source account grants sts:AssumeRole on that role to the right group. Policies can't be attached across accounts.

How do you give a CI pipeline access to AWS?

Preferably OIDC: an IAM OIDC identity provider for the CI system and a role trusting AssumeRoleWithWebIdentity, with aud and sub conditions pinned to the repo and branch or environment, so there are no long-lived keys. If OIDC isn't supported: a dedicated least-privilege user, keys in a secret store, rotated and monitored, with a migration plan.

What does arn:aws:iam::123456789012:root mean in a trust policy?

The whole account, not the root user. That account's own IAM policies decide which identities may assume the role.

An access key leaked. What do you do?

Deactivate it immediately, check CloudTrail (filter by access key ID) for what it did and from where, remediate any damage, delete it, issue a replacement only if needed, find out how it leaked, and move to roles or OIDC.

Permission boundary vs SCP?

Both only cap permissions and never grant. A boundary caps one user or role (e.g. roles that developers create). An SCP caps every identity in an account or OU, including admins, but not the management account.

What are AKIA / ASIA / AIDA / AROA?

AKIA = long-term access key · ASIA = temporary STS key · AIDA = IAM user ID · AROA = IAM role ID.

Why IMDSv2?

It requires a PUT to obtain a session token before credentials can be read, which blocks SSRF attacks that trick an app into fetching instance credentials (the Capital One 2019 breach).

Who did what in my account?

CloudTrail: Event history for the last 90 days of management events; an org-wide trail to S3 for long-term storage, queried with Athena. S3 object-level actions need data events enabled.
